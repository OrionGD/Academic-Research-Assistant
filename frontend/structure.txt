    user can still view the admin UI shell. A frontend role check is missing.

  1.3 API COMMUNICATION LAYER
  ─────────────────────────────────────────────────────────────────────────

    File: src/services/api/client.ts

    Architecture:
      - Single Axios instance (apiClient) shared across all service modules
      - Base URL: VITE_API_URL env var (falls back to '/api')
      - Timeout: 60 seconds (appropriate for large document operations)
      - Request Interceptor: Reads Firebase auth.currentUser and attaches
        the ID token as "Bearer <token>" header on every request
      - Response Interceptor: Global error handling with sonner toasts for
        401/403/404/429/500 status codes; redirects to /login on 401

    This is a well-designed pattern. Token refresh is manual
    (getIdToken(false) without force-refresh), which means stale tokens
    near expiry could cause 401s. Should use getIdToken(true) or implement
    a proactive refresh before expiry.

  1.4 STATE MANAGEMENT
  ─────────────────────────────────────────────────────────────────────────

    PLANNED (package.json): Zustand 5.0 + TanStack Query 5.90
    ACTUAL: Neither is used. All state is managed via:
      - React useState / useEffect in custom hooks
      - AuthContext (React Context API)
      - localStorage for chat history

    This is a significant architecture gap. Hooks like useDocuments.ts
    and useSearch.ts manually manage loading/error/data states, handle
    fetch calls, and maintain server-side state — exactly what TanStack
    Query is designed for. The absence of a proper caching layer means:
      - Every page mount triggers fresh API calls
      - No request deduplication
      - No background refetching
      - No optimistic updates
      - Chat history is only in localStorage (lost across devices)

    a drawer or hamburger menu overlay. The top navbar hides user details on

    layout (no Sheet/Drawer-based mobile nav, no hamburger overlay).

  1.8 IDENTIFIED PROBLEMS
  ─────────────────────────────────────────────────────────────────────────

    P1 (Critical): better-sqlite3 and express are in frontend package.json
       as runtime dependencies. These are Node.js-only packages that should
       never be bundled in a Vite frontend. frontend/server.ts appears to be
       a separate Express dev server using sqlite3 as a local mock database.
       This creates a hybrid monolith that confuses the architecture.

    P2 (High): No QueryClientProvider. Even though @tanstack/react-query is
       installed, there is no QueryClientProvider in main.tsx or App.tsx.
       If any page tries to use useQuery/useMutation it will throw at runtime.

    P3 (High): Chat history is persisted only in localStorage. Multi-tab,
       multi-device, and server-side session management are all absent.

    P4 (Medium): Token refresh strategy is passive (getIdToken(false)).
       Near-expiry tokens will fail on the next request, not proactively.

  2.2 REQUEST FLOW
  ─────────────────────────────────────────────────────────────────────────

    Document Upload:
    Client → POST /api/documents/upload
           → authMiddleware (Firebase token verify, user upsert)
           → apiLimiter (rate limit check)
           → multer (file buffer in memory, 10MB limit)
           → documentController.uploadDocument
               → GCS.save(buffer)           [file storage]
               → DocumentModel.save()        [metadata to MongoDB]
               → fetch('http://localhost:8000/process-document')  [ML service]
           → 201 { document }

    ISSUE: The document controller directly calls the ML service synchronously
    via fetch() instead of enqueuing a BullMQ job. The docQueue is created
    but never used in uploadDocument. The BullMQ workers are defined but
    NOT imported into server.ts, so they never start. Processing is therefore
    blocking and will time out on large PDFs.

    Semantic Search:
    Client → POST /api/search
           → authMiddleware
           → validateRequest(SearchRequestSchema)
           → searchController.executeSearch
               → fetch('http://localhost:8000/search')  [ML service]
           → JSON results

    ISSUE: The search controller builds docObjIds from user-owned documents
    but then calls the ML service with only the query (no userId or docIds).
    The ML service performs no user isolation. Any user's documents can be
    returned in search results.

    RAG Chat (Streaming):
    Client → POST /api/chat/stream
           → authMiddleware
           → validateRequest(ChatRequestSchema)
           → chatController.streamChat
               → fetch('http://localhost:8000/chat')  [ML service — synchronous!]
               → res.json(chatResponse)

    ISSUE: streamChat is named for SSE streaming but actually calls the ML
    service synchronously and returns a JSON response. The actual SSE
    streaming pipeline (ragChat.pipeline.ts) is never invoked. The
    runRagChatPipeline function is imported in chatController but never called.

  2.4 COMPILE ERRORS (from compile-errors.txt)
  ─────────────────────────────────────────────────────────────────────────

    The TypeScript compiler reports errors that PREVENT building the backend:

    ERROR 1 (Repeated x4 — Controllers + Workers):
      IORedis version conflict between top-level ioredis and BullMQ's bundled
      ioredis. BullMQ 5.x bundles its own ioredis version. When a separate
      IORedis instance is created and passed to BullMQ's Queue/Worker, the

      instead of creating an IORedis instance manually.

    ERROR 3 (textChunker.ts line 1):
      Cannot find module 'langchain/text_splitter'. The import is outdated.
      FIX: Import from '@langchain/textsplitters' (already in package.json).

    ERROR 4 (searchController.ts line 20):
      ObjectId[] | undefined passed where ObjectId expected.
      FIX: Handle the undefined case before passing to the search function.

    RESULT: The backend CANNOT be built (tsc compilation fails) in its current

  3.1 DOCUMENT INGESTION (pipelines/process.py)
  ─────────────────────────────────────────────────────────────────────────

    Step 1 — PDF Parsing:
      Uses PyMuPDF (page.get_text()) iterating over all pages.
      Returns raw concatenated text — no layout preservation, no table
      extraction, no figure/formula handling.

    Step 2 — Text Chunking:
      LangChain RecursiveCharacterTextSplitter
        chunk_size=1000, chunk_overlap=200
      This differs from the backend's chunkText() which uses
        chunk_size=700, chunk_overlap=150
      Two different chunking strategies for the same collection create
      inconsistent chunk sizes across the corpus.

    Step 3 — Embedding Generation:
      SentenceTransformer('all-MiniLM-L6-v2').encode(chunks)
      → 384-dimensional float32 vectors (batch, efficient)

    Step 4 — MongoDB Storage:
      Creates its own document record in db.documents with a UUID string
      ID (not a MongoDB ObjectId). Stores chunks in db.document_chunks
      with fields: documentId, chunkIndex, text, embedding.

    Step 5 — Summarization:
      STUB: Returns "Processed N chunks for filename." No real summarization.

    │    stores in: DocumentChunk.embedding (same collection)              │
    │                                                                      │
    │  MongoDB Atlas Vector Search Index:                                  │
    │    Can only be configured for ONE fixed dimension.                   │
    │    A 384-dim search query cannot match 768-dim stored vectors.       │
    │    A 768-dim search query cannot match 384-dim stored vectors.       │
    │                                                                      │
    │  RESULT: Vector search will return no results or incorrect results   │
    │  depending on which service embedded the documents vs. the query.   │
    └──────────────────────────────────────────────────────────────────────┘

  3.3 SEMANTIC SEARCH (pipelines/search.py)
  ─────────────────────────────────────────────────────────────────────────

    1. Encodes query with SentenceTransformer → 384-dim vector
    2. Executes $vectorSearch aggregation on document_chunks collection
       numCandidates: 100, limit: 5
    3. Returns top 5 chunks with text, documentId, and relevanceScore

    ISSUE — NO USER ISOLATION:
      The search pipeline has no filter by userId. Any authenticated user
      calling /search gets results from ALL documents in the collection,
      including documents uploaded by other users.

    ISSUE — NO SCORE THRESHOLD:
      Results are returned regardless of relevance score. Low-confidence
      matches will appear alongside highly relevant ones.

  3.4 RAG CHAT (pipelines/chat.py)
  ─────────────────────────────────────────────────────────────────────────

    1. Calls search_pipeline(message) → top 5 chunks
    2. Constructs prompt: system instruction + context text + user question
    3. Calls Gemini 2.5 Flash (synchronously, not streaming)
    4. Returns { message: { id, role, content }, citations: [documentIds] }

    ISSUES:
    - No conversation history — each call is stateless. The chat pipeline
      ignores prior messages entirely, creating a non-conversational bot.
    - Citations are document IDs (UUIDs), not actual document titles or
      page numbers. Frontend cannot render useful citations from this.
    - No streaming — response is returned as a single JSON blob. The
      Node.js backend has a full SSE streaming infrastructure (sseStream.ts,
      callGeminiStream) that goes completely unused.
    - Gemini API key initialized at module load with a "dummy" fallback,
      meaning the service starts silently broken if GEMINI_API_KEY is missing.

  3.5 MISSING ML PIPELINE STAGES
  ─────────────────────────────────────────────────────────────────────────

    - No OCR fallback for image-based PDFs (scanned documents will extract
      empty strings)
    - No mathematical formula preservation
    - No table extraction
    - No metadata extraction (authors, title, journal, year, DOI)
    - No language detection or multilingual support
    - No document deduplication check
    - No chunk quality filtering (empty/boilerplate chunks pass through)
    - No re-ranking beyond basic vector similarity
    - No hybrid search (BM25 + vector) for keyword-aware retrieval
    - No actual summarization in process.py (stubbed)

  SECTION 5 — AI PIPELINE ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  5.1 FULL PIPELINE STEP-BY-STEP
  ─────────────────────────────────────────────────────────────────────────

  STEP 1 — Document Upload
    Client sends multipart/form-data (PDF file + optional title).
    Multer buffers the file in memory (limit: 10MB).
    documentController.uploadDocument fires.
    File is uploaded to Google Cloud Storage (public URL generated).
    A Document record is created in MongoDB with status='processing'.

  STEP 2 — PDF Parsing
    Two independent paths exist:

    PATH A (Node.js — documentProcessing.pipeline.ts):
      Uses pdf-parse library → extractTextFromPdfBuffer()
      Returns raw text string with basic whitespace normalization
      (collapse 3+ newlines to 2, trim edges)

    PATH B (Python ML Service — process.py):
      Uses PyMuPDF (pymupdf) → page.get_text() for each page
      Returns raw concatenated string
      More capable than pdf-parse for complex PDFs (fonts, columns, etc.)

    Currently PATH B is used by the upload flow (direct fetch to ML service).
    PATH A is used by the BullMQ worker (never started).

  STEP 3 — Text Chunking
    Node.js: LangChain RecursiveCharacterTextSplitter
      chunkSize=700, chunkOverlap=150
    Python: LangChain RecursiveCharacterTextSplitter
      chunk_size=1000, chunk_overlap=200

    RecursiveCharacterTextSplitter splits on [\n\n, \n, " ", ""] in order,
    which is appropriate for academic text. However, academic papers have
    distinct sections (Abstract, Introduction, Methods, Results, Discussion)
    that would benefit from section-aware chunking to preserve semantic context.

    WEAKNESS: No metadata attached to chunks (page number, section name).
    WEAKNESS: No semantic chunking — paragraph boundaries may be split mid-idea.

  STEP 4 — Embedding Generation
    Node.js: Gemini text-embedding-004 via Google GenAI SDK
      Dimensions: 768
      Rate limit: subject to Gemini API quotas
      Processing: SEQUENTIAL — one chunk at a time (major bottleneck)

    Python: SentenceTransformers all-MiniLM-L6-v2
      Dimensions: 384
      Processing: BATCH (model.encode(chunks)) — efficient

    *** CRITICAL MISMATCH — see Section 3.2 ***

  STEP 5 — Vector Storage
    Chunks with embeddings stored to MongoDB documentchunks collection.
    Atlas Vector Search automatically indexes new documents if configured.
    Node.js uses DocumentChunk.insertMany() (efficient bulk insert).
    Python uses db.document_chunks.insert_many() (also efficient).

    WEAKNESS: No duplicate detection. Re-uploading same PDF creates
    duplicate chunks, bloating the vector index and polluting search results.

  STEP 6 — Semantic Search
    Python ML service:
      query → SentenceTransformer.encode() → 384-dim query vector
      → $vectorSearch (numCandidates: 100, limit: 5)
      → top 5 chunks by cosine similarity

    Node.js backend (semanticSearch.pipeline.ts):
      query → Gemini text-embedding-004 → 768-dim query vector
      → $vectorSearch (numCandidates: limit*10=50, limit: 5)
      → top 5 chunks by cosine similarity

    WEAKNESS: numCandidates=50 is very low for a recall-optimized system.
    MongoDB Atlas recommends numCandidates = 10-20× the limit. For 5 results,
    numCandidates should be 50-100 minimum, ideally 200+.

  STEP 7 — Context Retrieval
    Top-k chunks are retrieved and concatenated with '\n---\n' separators.
    Chat history (last 10 messages) is fetched from MongoDB.
    Context is assembled as raw text — no token counting, no trimming strategy.

    WEAKNESS: No token budget enforcement. A long conversation with multiple
    long chunks could exceed Gemini's context window. No graceful truncation.
    WEAKNESS: No source deduplication (same document chunk could appear
    multiple times if referenced by different queries in session history).

  STEP 8 — LLM Prompt Construction
    Node.js ragChat.pipeline.ts:
      System role: AI Academic Research Assistant
      Retrieved Context: concatenated chunk texts
      Conversation History: last 10 messages
      User Query
      Explicit instruction to cite chunk indices [Index <id>]

    Python chat.py:
      Shorter prompt with only context + question
      No conversation history included
      No citation instruction

    WEAKNESS: Prompt templates are partially duplicated between promptTemplates.ts
    and the inline prompts in pipelines. They diverge over time.

  STEP 9 — AI Response Generation
    Node.js: callGeminiStream() → server-sent events (SSE) via sseStream.ts
      Model: 'gemini-3.1-pro' ← THIS MODEL DOES NOT EXIST
      Valid models: gemini-1.5-pro, gemini-2.0-pro-exp, gemini-2.5-pro-preview

    Python: client.models.generate_content() (synchronous call)
      Model: 'gemini-2.5-flash' (valid)

    WEAKNESS: Model name 'gemini-3.1-pro' used throughout the Node.js backend
    (geminiService.ts default, analysisService.ts, semanticSearch.pipeline.ts)
    is invalid and will cause API errors at runtime for all AI features.

  5.2 PIPELINE WEAKNESSES SUMMARY
  ─────────────────────────────────────────────────────────────────────────

    FATAL:
    W1. Embedding dimension mismatch (384 vs 768) — vector search broken
    W2. Invalid LLM model name 'gemini-3.1-pro' — all Gemini calls fail
    W3. Backend TypeScript compile errors — backend won't build

    HIGH:

    W5. No conversation history in Python chat pipeline — not truly conversational
    W6. streamChat doesn't stream — SSE infrastructure unused
    W7. vectorSearchService projects 'text' but field is 'chunkText' — null results

    MEDIUM:

    W9. No OCR for scanned PDFs
    W10. Citations always empty array in analysis results
    W11. Duplicate document chunks on re-upload
    W12. No score threshold filtering (low-relevance chunks included)

  SECTION 6 — WORKER AND QUEUE SYSTEM ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  INFRASTRUCTURE:
    Queue Library: BullMQ 5.7
    Broker: Redis (via IORedis 5.4)
    Connection: redis://127.0.0.1:6379 (hardcoded fallback)

  6.1 WORKER DEFINITIONS
  ─────────────────────────────────────────────────────────────────────────

    documentProcessor.worker.ts
      Queue: 'document-processing'
      Job Data: { documentId, pdfBuffer?, userId, storagePath }
      Handler: runDocumentProcessingPipeline(documentId, userId, storagePath)
      Retry: attempts=5, backoff=exponential(1000ms)
      Events: 'completed', 'failed' (logged)
      STATUS: DEFINED BUT NEVER STARTED (not imported in server.ts)

    analysis.worker.ts
      Queue: 'document-analysis'
      Job Data: { documentId, userId, fullText }
      Handler: runAnalysisPipeline(documentId, userId, fullText)
      Retry: attempts=5, backoff=exponential(1000ms)
      Events: 'completed', 'failed' (logged)
      STATUS: DEFINED BUT NEVER STARTED (not imported in server.ts)

    vectorIndexer.worker.ts
      Queue: 'vector-indexer'
      Job Data: { documentId }
      Handler: Count chunks in MongoDB (verification only — no actual work)
      Retry: NONE CONFIGURED (no attempts/backoff options)
      Events: 'completed', 'failed' (logged)
      STATUS: DEFINED BUT NEVER STARTED (not imported in server.ts)

  6.2 HOW ASYNCHRONOUS TASKS ARE CURRENTLY HANDLED
  ─────────────────────────────────────────────────────────────────────────

    Despite BullMQ infrastructure being present, NO async queue processing
    occurs. The current flow is:

      Upload → Synchronous fetch to ML service → Wait for ML response → HTTP 201

    This means:
      - Large PDF processing blocks the HTTP request until the ML service finishes
      - If ML service takes >60s (Axios timeout), the client receives a timeout error
      - No retry mechanism applies (no BullMQ job was enqueued)
      - No job status tracking is possible
      - Server cannot handle concurrent uploads without resource exhaustion

  6.3 MISSING CONFIGURATIONS
  ─────────────────────────────────────────────────────────────────────────

    MISSING — Dead Letter Queue (DLQ):
      BullMQ supports a 'failed' queue for jobs that exhaust retries.
      No DLQ is configured. Failed jobs disappear silently after 5 attempts.
      Fix: Configure a 'dead-letter' queue and alert on DLQ additions.

    MISSING — Concurrency Limits:
      Workers have no concurrency setting (defaults to 1).
      Multiple documents can queue but only process one at a time.
      Fix: Set concurrency based on available CPU cores and API rate limits.
      Example: { connection, concurrency: 3 } for document worker.

    MISSING — Job Progress Reporting:
      Workers don't call job.updateProgress() at each pipeline stage.
      Clients have no way to poll job completion status.
      Fix: Report progress at each stage (10%, 30%, 60%, 90%, 100%).

    MISSING — Stalled Job Detection:
      No stalledInterval or lockDuration configured.
      Long-running embedding loops could stall without detection.

    MISSING — Queue Metrics:
      No monitoring endpoint exposes queue depth, wait time, or throughput.

    MISSING — Separate Worker Process:
      Workers should run in a separate process/service to isolate CPU-heavy
      operations from the API server. Currently they would (if started)
      compete for Node.js event loop time with API requests.

    CORRECTLY CONFIGURED:
      - Exponential backoff on both document and analysis workers ✓
      - attempts=5 on both (reasonable retry count) ✓
      - maxRetriesPerRequest: null on IORedis (required by BullMQ) ✓

  SECTION 7 — SECURITY ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  7.1 AUTHENTICATION
  ─────────────────────────────────────────────────────────────────────────

    GOOD:
    + Firebase ID tokens (JWT, short-lived ~1 hour) used as Bearer tokens
    + Firebase Admin SDK verifies token cryptographically server-side
    + Token expiry handled (auth/id-token-expired → 401)
    + User upserted into MongoDB on first login (no separate registration flow)
    + Google OAuth supported

    ISSUES:
    - authMiddleware is applied at '/api' but not for health check '/health'
      (intentional, low risk)
    - req.user typed as 'any' instead of 'IUser' — reduces type safety
    - No refresh token rotation strategy
    - Token is fetched without force-refresh (getIdToken(false)) — stale tokens
      possible in long sessions

  7.2 AUTHORIZATION
  ─────────────────────────────────────────────────────────────────────────

    GOOD:
    + All document queries include userId filter (owns-document check)
    + adminMiddleware checks req.user.role === 'admin'
    + Role is set to 'user' by default on creation

    ISSUES:
    - No admin promotion API endpoint — there is no way to set role='admin'
      through the API. An engineer must manually update MongoDB.
    - Frontend /admin route has NO role check — any logged-in user can
      navigate to the URL and see the admin UI shell (API calls will 401/403
      but UX is confusing and a data exposure risk from UI state)
    - aiEndpointLimiter is applied to /api/analysis routes but NOT to
      /api/chat/stream — expensive chat endpoints are unprotected from abuse

  7.3 RATE LIMITING
  ─────────────────────────────────────────────────────────────────────────

    Global (all /api routes):
      windowMs: 15 minutes, max: 100 requests per IP
    AI Endpoints (/api/analysis/start, /api/analysis/compare):
      windowMs: 1 minute, max: 10 requests per IP

    ISSUES:
    - Rate limits are IP-based only. Behind a shared NAT or reverse proxy, all
      users share the same IP limit (a single user can exhaust the limit for
      all users at the same IP)
    - /api/chat/stream has no AI-specific rate limit
    - No per-user rate limiting (a single authenticated user can exhaust the
      IP quota without affecting others, but also cannot be individually throttled)
    - No rate limiting on the Python ML service (no auth, no limits — completely
      open to abuse if accessible from the internet)

  7.4 INPUT VALIDATION
  ─────────────────────────────────────────────────────────────────────────

    GOOD:
    + Zod schemas validate all request bodies (search, chat, analysis, comparison)
    + ObjectId format validated with regex in validationSchemas.ts
    + validateRequest middleware is consistently applied to routes

    ISSUES:
    - File upload validation relies on mimetype field from client (spoofable).
      The fileFilter checks file.mimetype === 'application/pdf' but mimetype
      is set from the Content-Type header which clients control. Should also
      check magic bytes (file signature) of the buffer.
    - No maximum string length validation on 'title' field in document upload
    - fullText in AnalysisStartSchema: z.string().min(1) — a client could send
      millions of characters, causing memory pressure and excessive Gemini costs
    - Python ML service has NO input validation beyond FastAPI's basic Pydantic
      model type checking

  7.5 FILE UPLOAD SECURITY
  ─────────────────────────────────────────────────────────────────────────

    Backend limit: 10MB (Multer)
    Frontend check: 50MB (useDocuments.ts)
    MISMATCH: Frontend allows files the backend will reject with a 413.

    ISSUES:
    - Buffer stored in memory (multer.memoryStorage()) — a 10MB file means
      10MB in Node.js heap during upload. Concurrent large uploads could
      exhaust memory.
    - GCS URL is constructed as a public URL without authentication:
      'https://storage.googleapis.com/{bucket}/documents/{userId}/{filename}'
      If the GCS bucket is not properly secured, files are publicly accessible
      without authentication via this URL.
    - The GCS storage URL is stored in MongoDB and could be harvested by an
      admin-role user to access any user's PDFs directly from GCS.

  7.6 API ABUSE PROTECTION
  ─────────────────────────────────────────────────────────────────────────

    GOOD:
    + express-rate-limit in place
    + Auth required on all /api routes

    ISSUES:
    - CORS configured with app.use(cors()) — NO configuration. This allows
      ALL origins, ALL methods, ALL headers. Should restrict to the known
      frontend origin (VITE_API_URL domain).
    - Python ML service CORS: allow_origins=["*"] — completely open
    - MongoDB URI hardcoded in ml-service/services/db.py with real credentials:
      MONGO_URI = "mongodb+srv://aras_rag:aras_rag192607@aras.jnqzklv.mongodb.net/"
      This is a CRITICAL security vulnerability — credentials in source code.
    - No HTTPS enforcement (no helmet.js, no HSTS headers)
    - No Content-Security-Policy headers
    - Express version info exposed in response headers (should use helmet
      to set X-Powered-By: false)

  SECTION 8 — PERFORMANCE ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  8.1 LARGE PDF FILES
  ─────────────────────────────────────────────────────────────────────────

    RISK: HIGH
    - 10MB PDF can generate 500-1000 chunks (at 700 chars/chunk)
    - Each chunk requires a Gemini API call (text-embedding-004)
    - At ~200ms/call, 1000 chunks = 200 SECONDS of sequential processing
    - Node.js Axios timeout is 60 seconds → request will time out
    - The file buffer is held in memory during this entire time

    OPTIMIZATION RECOMMENDATIONS:
    1. Enqueue a BullMQ job (don't process synchronously in request handler)
    2. Batch embed requests (Gemini supports up to 100 texts in one call via
       batchEmbedContents API)
    3. Use GCS streaming instead of full buffer download
    4. Implement chunked progress reporting via WebSocket or polling endpoint

  8.2 VECTOR SEARCH QUERIES
  ─────────────────────────────────────────────────────────────────────────

    RISK: MEDIUM
    - $vectorSearch with numCandidates=50 (limit*10 for limit=5) is low.
      This reduces recall — relevant chunks may be missed.
    - Reranking via Gemini (in semanticSearch.pipeline.ts) adds another
      500-1000ms LLM call on top of the vector search
    - No caching — identical queries hit the database every time

    OPTIMIZATION RECOMMENDATIONS:
    1. Increase numCandidates to 200 for better recall
    2. Cache search results in Redis with query hash as key (TTL: 5 minutes)
    3. Implement hybrid search: combine vector score with BM25 text score
       (MongoDB Atlas supports $search with hybrid scoring)
    4. Pre-filter by documentId at the vector search stage when documentIds
       are provided to reduce search space

  8.3 EMBEDDING GENERATION LATENCY
  ─────────────────────────────────────────────────────────────────────────

    RISK: CRITICAL (blocks uploads)
    - Sequential API calls to Gemini for each chunk (see 8.1)
    - No batching, no parallelism, no rate-limit-aware queuing

    OPTIMIZATION RECOMMENDATIONS:
    1. Use Gemini's batch embedding endpoint (embedContent with multiple contents)
    2. Process in parallel with controlled concurrency (p-limit or Promise.all
       with batches of 10-20 chunks)
    3. Switch to self-hosted embedding model (same as Python service) to
       eliminate API latency — SentenceTransformers runs locally

  8.4 REDIS QUEUE LOAD
  ─────────────────────────────────────────────────────────────────────────

    RISK: LOW (currently, because queues are not used)
    When queues are activated, risks include:
    - Multiple IORedis connections (one per worker, one per controller)
      Instead: share a single connection factory
    - No connection pooling configuration
    - Redis persistence not configured (AOF/RDB) — job data lost on restart

    OPTIMIZATION RECOMMENDATIONS:
    1. Create a shared redisConnection module imported by all workers/controllers
    2. Configure Redis with AOF persistence for job durability
    3. Set maxRetriesPerRequest: null only on BullMQ connection, not on all connections
    4. Monitor queue depth via BullMQ's getJobCounts()

  8.5 MONGODB VECTOR SEARCH PERFORMANCE
  ─────────────────────────────────────────────────────────────────────────

    RISK: MEDIUM-HIGH at scale
    - Atlas Vector Search uses HNSW index — O(log n) at query time, good
    - Performance degrades with very large collections without pre-filtering
    - No index on (userId + documentId) combination for filtered searches
    - Storing large embedding arrays (768 floats = ~6KB per chunk) inflates
      document size and memory pressure

    OPTIMIZATION RECOMMENDATIONS:
    1. Use Atlas Vector Search 'filter' parameter to pre-filter by userId
       (already implemented in vectorSearchService — good)
    2. Add compound index: { userId: 1, documentId: 1, chunkIndex: 1 }
    3. Consider quantizing embeddings (int8) to reduce storage by 4×
    4. Archive old chat messages to a separate collection after 90 days

  SCORE JUSTIFICATION:

  The system demonstrates a sophisticated and thoughtful architectural design.
  The choice of BullMQ for async processing, MongoDB Atlas Vector Search for
  embeddings, Firebase Auth for identity, SSE for streaming, and Zod for
  validation all reflect competent engineering decisions. The pipeline
  abstractions are clean and well-organized.

  However, the system CANNOT be deployed to production in its current state:

  1. The TypeScript backend DOES NOT COMPILE (5 errors in compile-errors.txt).
     This alone is a hard blocker for any production deployment.

  2. The AI pipeline core is functionally broken — the embedding dimension
     mismatch (384 vs 768) means vector search will never return meaningful
     results. This is the product's primary value proposition.

  3. The invalid LLM model name 'gemini-3.1-pro' will cause every Gemini
     API call from the Node.js backend to throw an error.

  4. The BullMQ workers are defined but never start. All document processing
     is synchronous and will time out on any real-world PDF.

  5. Security posture is weak — hardcoded DB credentials, open CORS, no
     authentication on the ML service, no HTTPS headers.

  The system is best characterized as a well-structured proof-of-concept or
  late-stage prototype. Substantial work remains across all dimensions before
  production readiness is achieved.
